# AIOps Incident Manager

An AI-powered IT incident management platform: support tickets are
automatically classified and routed to the right team using a
TF-IDF + Random Forest model, tracked through their lifecycle via a
Django REST API, and engineers get real-time alerts for critical
incidents over WebSockets.

Built with **Django, Django REST Framework, PostgreSQL, scikit-learn,
Redis/Django Channels, Docker, and GitHub Actions**.

## Overview

When an end user reports an IT issue ("VPN connection failing for
remote employee"), this system:

1. Creates a `Ticket` via the REST API.
2. Runs the description through a trained **TF-IDF + Random Forest**
   pipeline to predict which support team should own it (`NETWORK`,
   `DATABASE`, `SECURITY`, `CLOUD`, `APPLICATION`, or `DEVOPS`) and
   stores the model's confidence score.
3. Sets an SLA due date based on priority (e.g. 2 hours for
   `CRITICAL`, 72 hours for `LOW`).
4. If the ticket is `CRITICAL`, creates `Notification` records for
   every engineer on the assigned team and pushes a real-time alert
   over a WebSocket (`/ws/notifications/`) via Django Channels.
5. Exposes everything through a documented REST API (Swagger/OpenAPI
   via drf-spectacular), with JWT authentication and role-based
   permissions (`USER`, `ENGINEER`, `ADMIN`).

## Architecture

```
                ┌──────────────┐        ┌─────────────────────┐
   Client  ───▶ │  Django REST │ ─────▶ │  PostgreSQL (RDS)    │
 (HTTP/JSON)    │  Framework   │        │  tickets, users,     │
                │  (DRF)       │        │  notifications       │
                └──────┬───────┘        └─────────────────────┘
                       │
                       │ on Ticket creation
                       ▼
                ┌──────────────┐
                │  ml_router    │  TF-IDF + Random Forest
                │  classifier   │  (joblib pipeline, loaded once)
                └──────┬────────┘
                       │ assigned_team, confidence
                       ▼
                ┌──────────────┐
                │  Notification │ ── Redis Pub/Sub ──▶ Django Channels
                │  model + push │                       (other workers)
                └──────┬────────┘
                       │
                       ▼
            WebSocket /ws/notifications/
              (engineer's browser/app)
```

In production (AWS), the Django app runs as a containerized service on
**ECS** behind an ALB, backed by **RDS PostgreSQL** and
**ElastiCache Redis** for the Channels layer:

```
 Internet -> ALB -> ECS Service (Django/Daphne containers, autoscaled)
                       |             |
                       v             v
                 RDS PostgreSQL   ElastiCache Redis
```

## Features

- **JWT authentication** (`djangorestframework-simplejwt`) with
  register / token / refresh endpoints.
- **Role-based access control** -- `USER`, `ENGINEER`, `ADMIN` roles;
  engineers are scoped to their team's tickets.
- **Ticket lifecycle management** -- priority, status, SLA due dates,
  comments, overdue detection.
- **ML-based ticket routing** -- TF-IDF + Random Forest pipeline,
  trained on a labeled dataset of ~750 ticket descriptions across 6
  support teams.
- **`/api/predict-team/`** -- standalone endpoint to preview routing
  for any description.
- **Real-time alerts** -- Django Channels + Redis pub/sub push
  `CRITICAL` ticket notifications to the right team's engineers over
  WebSockets.
- **Swagger / OpenAPI docs** at `/api/docs/`.
- **Pytest test suite** covering auth, ticket CRUD + permissions, ML
  routing, and notifications.
- **Dockerized** with `docker-compose` (Django + PostgreSQL + Redis).
- **GitHub Actions CI** -- lint, Django checks, migrations, and tests
  with coverage on every push/PR.
- **Demo data seeder** (`seed_demo_data`) for quick exploration.

## ML Ticket Routing Model

The routing model lives in `model_training/` and is loaded by the
Django app from `backend/ml_router/trained_model/ticket_router.pkl`.

| Step | Details |
|---|---|
| Dataset | `model_training/ticket_dataset.csv` -- ~750 synthetic-but-realistic ticket descriptions labeled with one of 6 teams, generated by `generate_dataset.py`. Includes deliberately ambiguous tickets and ~6% label noise to avoid an unrealistically "easy" dataset. |
| Features | `TfidfVectorizer` (unigrams + bigrams, English stopwords removed, max 2000 features) |
| Model | `RandomForestClassifier` (200 trees) |
| Result | **87.3% test accuracy** across 6 classes (see `backend/ml_router/trained_model/metrics.json` for the full classification report) |

To retrain the model (e.g. after editing the dataset/templates):

```bash
cd model_training
python generate_dataset.py    # regenerate ticket_dataset.csv
python train_model.py         # retrains and overwrites the .pkl + metrics.json
```

**Why TF-IDF + Random Forest instead of a transformer/LLM?** It's a
fast, dependency-light, fully-explainable baseline: it trains in
seconds on a laptop with no GPU, `feature_importances_` make it easy
to debug *why* a ticket was routed a certain way, and it's "good
enough" for short, templated support-ticket text. See
[Future Improvements](#future-improvements) for how this could be
extended with an LLM-based router.

## Getting Started

### Option A: Local (SQLite, no Docker)

Requires Python 3.12+.

```bash
git clone https://github.com/vasavikosaraju-collab/aiops-incident-manager.git
cd aiops-incident-manager

python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt

cp .env.example .env            # defaults to SQLite + in-memory channel layer

cd backend
python manage.py migrate
python manage.py seed_demo_data   # optional: creates demo users + tickets
python manage.py createsuperuser  # optional: your own admin account

python manage.py runserver
```

Visit:

- API docs: http://127.0.0.1:8000/api/docs/
- Admin: http://127.0.0.1:8000/admin/

### Option B: Docker Compose (PostgreSQL + Redis)

This mirrors the production setup more closely (PostgreSQL +
Redis-backed Channels layer).

```bash
docker compose up --build
```

Then, in another terminal:

```bash
docker compose exec web python manage.py seed_demo_data
docker compose exec web python manage.py createsuperuser
```

The API is available at http://localhost:8000/, docs at
http://localhost:8000/api/docs/.

## API Reference

All endpoints are documented interactively at `/api/docs/`. Highlights:

### Auth

```bash
# Register
curl -X POST http://localhost:8000/api/auth/register/ \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "StrongPass123!", "email": "alice@example.com"}'

# Get a token
curl -X POST http://localhost:8000/api/auth/token/ \
  -H "Content-Type: application/json" \
  -d '{"username": "alice", "password": "StrongPass123!"}'

# Current user
curl http://localhost:8000/api/auth/me/ \
  -H "Authorization: Bearer <access_token>"
```

### Tickets

```bash
# Create a ticket (auto-routed by the ML model)
curl -X POST http://localhost:8000/api/tickets/ \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{
        "title": "Cannot connect to VPN",
        "description": "VPN connection failing for remote employee",
        "priority": "HIGH"
      }'

# -> response includes "assigned_team": "NETWORK", "routed_confidence": 0.83

# List my tickets / filter
curl "http://localhost:8000/api/tickets/?status=OPEN&priority=CRITICAL" \
  -H "Authorization: Bearer <access_token>"

# Update status (engineers/admins only)
curl -X PATCH http://localhost:8000/api/tickets/1/ \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"status": "RESOLVED"}'

# Add a comment
curl -X POST http://localhost:8000/api/tickets/1/comments/ \
  -H "Authorization: Bearer <access_token>" \
  -H "Content-Type: application/json" \
  -d '{"body": "Investigating now."}'
```

### ML Routing Preview

### Real-time WebSocket

Connect (with an authenticated session -- see
`notifications/consumers.py`) to:

```
ws://localhost:8000/ws/notifications/
```

Engineers receive a JSON payload whenever a `CRITICAL` ticket is routed
to their team:

```json
{
  "type": "incident_alert",
  "ticket_id": 42,
  "title": "Production database is extremely slow",
  "priority": "CRITICAL",
  "assigned_team": "DATABASE",
  "message": "New CRITICAL ticket #42: 'Production database is extremely slow' routed to DATABASE"
}
```

## Design Decisions

A few choices worth being able to explain (e.g. in an interview):

- **Why a custom User model with a `role`/`team` field instead of
  Django groups/permissions?** It's simpler to reason about for a
  small number of coarse-grained roles, and lets ticket routing and
  visibility be expressed as plain queryset filters
  (`tickets/views.py::get_queryset`).
- **Why `Ticket.objects.filter(pk=...).update(...)` in
  `tickets/signals.py` instead of `instance.save()`?** Calling `save()`
  again inside a `post_save` handler would re-trigger `post_save`
  (infinite loop risk) and re-run the SLA-setting logic in
  `Ticket.save()`. A targeted `.update()` avoids both issues.
- **Why an in-memory Channels layer by default?** So the project runs
  and the test suite passes with zero extra infrastructure. Set
  `CHANNEL_LAYER_BACKEND=redis` (as `docker-compose.yml` does) for
  real multi-process delivery, which is required once you run more
  than one Django worker.
- **Why SQLite by default but PostgreSQL in Docker/CI?** Fast local
  iteration without installing Postgres, while CI and
  `docker-compose` exercise the same PostgreSQL setup used in
  production (catching DB-specific issues like migration ordering).

## Future Improvements

- **LLM-assisted incident summarization** -- use an LLM to generate a
  human-readable summary, likely root cause, and suggested next steps
  for a ticket, optionally grounded in similar past tickets (RAG over
  resolved tickets).
- **Auto-priority suggestion** -- `ticket_dataset.csv` already includes
  a `priority` column that isn't used by the current model; a second
  classifier (or a multi-output model) could suggest priority
  alongside team.
- **SLA breach alerts** -- a periodic Celery task that scans for
  `is_overdue` tickets and notifies engineers/managers.
- **AWS ECS deployment** -- Terraform/CDK for an ECS service (this
  Docker image), RDS PostgreSQL, ElastiCache Redis, and an ALB with
  autoscaling based on CPU/request count.
